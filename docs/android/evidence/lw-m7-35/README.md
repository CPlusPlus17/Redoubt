`WebExtensionController.getAutomaticUpdateSettings()` reports both effective booleans, combined `enabled`, `locked`, and `saveConfirmed`. `setAutomaticUpdateSettings(boolean)` serializes choices, closes automatic admission as soon as one is queued, validates locks, verifies the current-profile write path before mutation, writes the pair, and awaits the real write result. `saveConfirmed=false` records a controller change without a successful save acknowledgment. Reads cannot clear it. Failed persistence leaves actual current native values intact, reports unconfirmed disk state in the UI, and holds automatic admission closed until a successful save. It performs no inferred rollback, including when another writer sets the same value. The API can retry the same value. Navigating away does not cancel an accepted choice; late callbacks cannot rewrite a destroyed or newer view. A failed write does not establish what bytes reached disk.

Periodic and restored WorkManager jobs use `updateAddonAutomatically` → `updateWebExtensionAutomatically` → `WebExtensionController.updateAutomatically`. Existing immediate-work tags identify explicit requests and notification consent; unknown/restored work defaults to the automatic route. Native automatic admission checks before repository metadata, after metadata/extension lookup, and before starting the XPI install. Ordinary XPI install paths are untouched.

Explicit update requests use the existing `update` API and `UPDATE_WHEN_USER_REQUESTED`; automatic requests use `UPDATE_WHEN_PERIODIC_UPDATE`. Turning automatic updates off does not cancel an install already started. Mixed native values (update.enabled=true, autoUpdateDefault=false) appear unchecked, as on desktop, while permitting metadata checks and a per-addon explicit Enable override. Choosing Off in this switch sets **both** false. This is an extension-update control, not a ban on unrelated extension catalog reads or locale-change metadata refreshes.

The new `nsIPrefService.savePrefFileAsync()` forces an ordered current-profile snapshot and resolves only its actual write success. No initialized profile or profile shutdown rejects before any snapshot. Each `PWRunnable` owns its snapshot/destination/promise on the existing serial I/O target; the old shared snapshot could be consumed by another request or written to another file. The old callback also resolved a failed write as true. Dispatch failure explicitly rejects and balances the pending count, even if dispatch retains the runnable. Blocking saves obtain the wrapped write result (SyncRunnable itself only reports dispatch status), force the latest snapshot even when the dirty flag was cleared by an earlier asynchronous save, and preserve pre-profile backup flushing. Failed final saves do not mark the profile shut down. Dirty/error bookkeeping stays on the main thread; promise completion uses the real I/O result independently. Cancellation releases the file on the main thread. This Android-only registered patch also changes legacy pref-save/backup scheduling from shared coalescing to distinct snapshots: additional writes/memory are an explicit cost. The desktop patch list is unchanged.
