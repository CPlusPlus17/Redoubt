# Runtime pref audit (LW-M3-05)

The runtime pref audit is the regression net for the M3 privacy decisions.
It catches a rebase, a Fenix update, or an upstream change **quietly
reverting a privacy pref at runtime** — the failure shape that static
source checks (REBASE.md §6a–6d) can only predict, because they cannot see
a pref whose effective value differs from its declared default, a pref
written by a Fenix code path that never declares it, or a pref set through
a `GeckoRuntimeSettings` builder method.

## Files

| File | Role |
|---|---|
| `scripts/android-pref-audit.sh` | The gate. Dumps effective pref values from a running build, diffs against the baseline, fails only on must-lock violations. |
| `scripts/generate-android-pref-baseline.sh` | Regenerates the baseline from a running build. The baseline is **generated, never hand-written**. |
| `docs/android/expected-prefs.txt` | The checked-in baseline. Tab-separated pref-dump v1 payload (see format below). |
| `docs/android/must-lock.txt` | **Source of truth for which keys the audit may fail on.** Generated by `scripts/gen-android-locks.py` (LW-M3-04); regenerate with `python3 scripts/gen-android-locks.py`. |

## The dump format

The smoke harness (`scripts/android-smoke.sh --pref-dump`) prints a fixed,
curated list (`PREF_LIST`, `android-smoke.sh`) of security- and
privacy-relevant prefs as a tab-separated payload on **stdout only**
(progress goes to stderr, so a pipeline can diff or store stdout verbatim):

```
# librewolf-android-smoke pref-dump v1
# name	type	value	locked	user
browser.contentblocking.category	string	strict	locked	-
```

Columns: pref name, type (`bool`/`int`/`string`, or `missing` if the pref
does not exist in this build), the effective value, whether the pref is
locked, and whether it has a user-set value. Both the baseline and the
audited dump are in this format, which is what the comparison relies on.

## How the audit works

`scripts/android-pref-audit.sh`:

1. **Preflight.** Fails with exit 2 if the smoke harness, the must-lock
   list, or the baseline is missing or malformed — never with a silent
   pass.
2. **(a) Drive the settings UI — placeholder.** A full audit walks every
   settings screen (open each, toggle nothing) *after* the app starts and
   *before* the dump, so the `Pref.commit()` calls Fenix fires when its
   settings screens open (AGENTS.md, landmine L2, stage 5b) are included in
   the audited state. This repository's local execution capabilities do not
   include that automation — see the Gap Declaration. The step is a
   documented no-op for now.
3. **(b) Take the dump.** Runs `./scripts/android-smoke.sh --pref-dump`
   into a temporary file (stdout and stderr kept separate) and validates
   that the payload is a non-empty pref-dump v1 payload.
4. **(c) Compare.** Because the format is tab-separated, the comparison is
   **key-based via `awk`, not a line diff**: each key's recorded state
   (type, value, lock and user annotations) is compared by name, so row
   reordering is noise, not a difference.
5. **(d) Filter.** Only diffs on keys listed in `must-lock.txt` are
   violations.
6. **(e) Exit.** 1 on any violation, 0 otherwise, 2 if it could not run.

## The filtering logic — why only must-lock keys can fail

The baseline is a *curated* list; not every key in it is a must-lock key,
and `must-not-lock.txt` exists precisely because some keys the settings UI
owns **must be allowed to move**. A line-diff of the whole dump would
therefore fail the gate on changes that are legitimate by design. The audit
instead partitions every difference:

- **must-lock key, state differs from baseline → `VIOLATION`** (exit 1).
  Includes a change of value, type, or lock status, and a key that is
  present in one file but absent from the other (a must-lock pref missing
  from the actual dump is the landmine-L1 shape: the guard is gone).
- **must-lock key in *neither* file → out of scope, not a violation.**
  The harness only dumps its fixed `PREF_LIST`; the other must-lock keys
  (e.g. `javascript.enabled`, `apz.allow_double_tap_zooming`) are enforced
  by the generated locks of LW-M3-04 instead. Counting their absence here
  would make the gate red for a healthy build, so the report prints how
  many must-lock keys fall outside the dump universe.
- **any other key, any difference → `NOTE`** (never fails). These are
  printed so a shrinking of audit coverage is visible in the output
  without turning a legitimate setting into a gate failure.

`must-lock.txt` is the single source of truth for the first partition: it
is generated, not hand-maintained (36 of its 137 names are constructed by
`SafeBrowsingProvider` code and invisible to a hand-built list), and the
audit re-reads it on every run.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Every must-lock pref the harness dumps matches the baseline. |
| 1 | At least one must-lock pref is missing from or differs from the baseline. **The gate is red.** |
| 2 | The audit could not run at all (harness missing, baseline missing, no device/APK, malformed payload). **Never a pass, never a violation** — per the house rule that a gate with a missing input must fail loudly. |

Note the smoke harness's own contract (`android-smoke.sh` header): 0 = pass,
1 = a check failed, 2 = harness could not run, 3 = flag not implemented.
Any non-zero exit from `--pref-dump` makes the audit exit 2 with the
harness's stderr, so a harness error is never confused with a pref
violation.

## Generating the baseline

```sh
./scripts/generate-android-pref-baseline.sh
```

Requirements: a running Android environment (the harness can boot an
emulator with `--emulator`, or point `--serial`/`--sdk`/`LW_SMOKE_APK` at
your setup — see `docs/android/SMOKE.md`). The script:

- runs `./scripts/android-smoke.sh --pref-dump`, keeping stdout (payload)
  and stderr (progress) separate;
- fails with exit 2 and leaves any existing baseline untouched if the
  harness is missing, fails, or produces a malformed/empty payload;
- stages the payload and atomically renames it over
  `docs/android/expected-prefs.txt` (readers never see a partial file);
- reports how many lines were added/removed against the previous baseline.

A baseline change is a **review event**: it means either the build's
effective prefs moved (which may be the regression the audit exists to
catch) or the harness's `PREF_LIST` changed. Read the diff before
committing.

## Using it in CI

Invoke the script directly; it owns its own exit code. There is no pipeline
to guard — the audit writes the dump to a temporary file itself, so the
"watch out for pipelines" trap from `SMOKE.md` does not apply to it.

## Gap Declaration

**This audit cannot run in this repository's local execution environment,
and that must be said out loud rather than discovered at 2 a.m.**

1. **A running Android environment is required.** The audit's input is the
   smoke harness's `--pref-dump`, which needs a live GeckoView session: an
   emulator or a physical device, an installed APK, and adb. On a machine
   without one, `android-smoke.sh` exits 2 and the audit exits 2 as well —
   it does **not** pass, and it must never be treated as passing.

2. **A UI automation script to drive the app is required for full
   coverage.** A complete audit walks every settings screen before the
   dump (step (a)), because Fenix commits prefs when settings screens open
   (landmine L2, stage 5b) and a pref that only moves when a screen opens
   is invisible to a post-startup dump. No such automation script exists in
   this repository's local execution capabilities; step (a) is therefore a
   documented placeholder no-op, and the audit currently covers the
   post-startup state only.

3. **Consequence for the checked-in baseline.**
   `docs/android/expected-prefs.txt` does not exist in this repository yet
   (see REBASE.md §6e). It must be generated by
   `scripts/generate-android-pref-baseline.sh` on a machine that satisfies
   points 1 and 2, and that generation — on a real device or emulator,
   against a real APK — is the evidence that the baseline is real. Until
   it lands, the audit exits 2 by design, and a rebase must be recorded as
   "source-level pref checks clean; runtime audit not available
   (LW-M3-05)", exactly as REBASE.md §6e requires.

Nothing in this document or the two scripts is a substitute for that run.
A baseline produced anywhere other than against a running Android build is
a claim without provenance, and the audit will happily enforce whatever
claim it is handed.
